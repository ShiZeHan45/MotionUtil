# 小白视角讲稿规范

版本：1.3
适用范围：节点 3 生成的项目讲稿、原理故事板、案例说明和操作说明。

## 1. 核心目标

视频的目标不是把 README 念一遍，而是让第一次接触这个项目的人，在三分钟内回答四个问题：

1. 它解决了什么具体麻烦？
2. 谁在什么时候做了什么？
3. 这些动作为什么能得到结果？
4. 我怎样判断它适不适合自己的场景？

“小白视角”不等于删掉技术事实，也不等于把技术讲成夸张的比喻。所有事实、数字、支持范围和限制仍然必须来自节点 2 已采集的项目资料；没有资料就明确说资料没有提供。

## 2. 固定叙事顺序

视频只讲原理、案例和总结，不讲安装和操作步骤（2026-10-14 起）。每个项目共六段，顺序固定，每一段的例子、比喻和图形要根据项目内容变化：

1. **开场**（intro）：只写所选的一句知识钩子；榜单名次、项目名和累计 Star 由程序补一句固定句式。
2. **现实麻烦**（problem）：用一个普通用户会遇到的场景说明问题，不先堆项目名和技术名词。
3. **原理拆解**（concept）：按“输入或参与者 → 动作 → 中间变化 → 结果”逐步讲。每讲一个动作，画面才出现对应元素；画面优先用卡通比喻动画。
4. **具体案例**（case）：围绕原理中的同一个任务走一遍，不能换成另一个无关示例。
5. **结果检查**（dashboard）：说明用户能看到什么、检查什么，以及什么现象不能证明任务已经完成。
6. **结论**（summary）：用日常语言重新回答开场问题，并用一句话说明适合谁、有什么边界。

## 3. 每句话的写法

推荐顺序：

> 具体情境 → 日常动作 → 结果变化 → 必要术语

例如：

- 不推荐：OpenRig 通过持久团队、共享上下文和 owned work 实现多代理编排。
- 推荐：先把谁写代码、谁检查写进团队配置。启动后，每个助手有自己的运行会话。这样多个助手可以按分工接任务；这份配置文件使用 YAML 格式。

每句话尽量只推进一个意思。一个句子同时出现多个新名词时，拆成两到三句。第一次出现术语时，先解释它解决的麻烦，再给名称：

| 术语 | 第一次出现时的表达方式 |
| --- | --- |
| YAML | 一份写清谁负责什么的配置文件，格式叫 YAML |
| tmux | 管理多个终端运行会话的工具，叫 tmux |
| 队列 | 按顺序保存待办任务的清单，也就是任务队列 |
| API | 程序之间约定好的调用入口 |
| agent | 负责一项工作的编程助手；必要时再保留 agent 这个名称 |
| builder / reviewer | 写代码的助手 / 检查代码的助手 |

术语解释必须准确。不能为了通俗，把“消息送达”说成“任务已经完成”，也不能把“可以理解成”说成项目内部一定就是这样实现的。

## 4. 比喻和案例规则

- 比喻只解释已经被资料支持的关系，不能借比喻补造内部实现。
- 比喻必须紧接着落回项目事实：先说“可以把它理解成……”，随后说明项目资料实际确认的动作。
- 没有官方或社区实例时，可以使用明确标注为“假设场景”的语义案例；不能伪造产品截图、用户效果或性能数字。
- 案例必须包含目标、参与者、动作、结果和检查方式；不能只展示一张装饰图片。
- 不把 Stars、npm version、downloads、coverage、license 或 build badge 当作案例证据。

## 5. 画面和口播同步

原理不是先铺满一张图，再用口播解释。每个 beat 必须对应一个正在发生的动作：

1. 口播说到一个参与者或对象时，绘制它。
2. 口播说到动作时，绘制动作路径或消息。
3. 口播说到状态变化时，高亮变化前后的状态。
4. 口播说到结果时，再显示结果和检查方法。

图形类型按项目语义选择：

- 多角色协作和任务分派：简化泳道图或时序图。
- 输入经过处理产生输出：数据流图。
- 安装、判断、重试和失败分支：活动图。
- 状态从等待到运行再到完成：状态图。

不使用完整 UML 的复杂符号。只保留普通观众能读懂的角色、动作、状态和方向。图形标题和标签是短提示，完整解释由同步口播和字幕承担。

## 6. 禁止写法

- 不要逐句翻译 README 的抽象措辞。
- 不要把功能清单当成原理解释。
- 不要连续堆叠三个以上未解释的英文缩写。
- 不要用“然后、接着、最后”串联一堆没有因果关系的卡片。
- 不要先展示所有对象，再补一句“它们共同协作”。
- 不要把操作步骤写成散点功能介绍；操作口播必须按“第一步、第二步……”顺序推进。
- 不要用“高效、强大、无缝、革命性、轻松解决”等没有资料依据的评价词。
- 不要把模型的分析、审核理由、【待填】占位符或提示词写进字幕和配音。
- 不要用 CTA、下载引导或带货话术替代知识价值。

## 7. 节点 3 的生成检查清单

生成前：

- 是否已经从节点 2 的原文提炼事实，并记录来源和句序号？
- 是否确定目标观众和一个具体任务？
- 是否为原理选择了最合适的图形类型？

生成后：

- 开场问题是否能在原理段得到明确答案？
- 每个新术语是否在首次出现附近得到解释？
- 每个原理 beat 是否只有一个主要动作？
- 案例和操作是否围绕同一个任务？
- 每个图形对象是否被口播解释，是否有明确关系？
- 画面元素是否按照口播顺序出现，而不是一开始全部出现？
- 是否存在没有来源的数字、功能、比较、效果或内部机制？
- 文字是否完整显示，是否有卡片、标签或字幕溢出？

## 8. 质量判定（内容审稿门槛）

以下任一项失败，讲稿在内容审稿中不能进入节点 4：

- 只能复述项目名和功能，无法说清它解决的具体麻烦。
- 读者必须先懂术语，才能理解句子。
- 开场提出的问题没有在原理或案例中兑现。
- 画面对象与口播不同步，或对象之间的关系没有被说明。
- 案例不是资料支持的实例，也没有明确标注为假设场景。
- 核心文字被截断、翻页时丢句，或审核信息进入正式配音。

其中“能否说清麻烦”“比喻是否准确”“是否听得懂”属于人工内容审稿，当前程序不会自动判定通过，也不会仅凭这份清单阻止节点 4。程序校验负责检查来源、字段、顺序、长度、对象关系、时长和布局。首批新稿仍需人工听读一遍，重点检查“听完是否能复述项目怎么工作”；发现失败时应从节点 3 重新生成或修改讲稿，再进入节点 4。

## 9. 记忆接入方式

这份文档是产品和编剧的规范来源。节点 3 的系统提示词需要保留其中的硬规则，并在规则有变化时同步修改 PROMPT_VERSION；节点 3 的结构化校验负责拦截来源、顺序、对象关系、时长和溢出问题；节点 4 和节点 5 只消费通过验收的讲稿与故事板。

修改本规范后，旧讲稿不会自动改变。要应用新规范，必须从节点 3 重新生成，再执行节点 4 和节点 5。

## 10. 表达密度与连贯性（1.2 新增硬规则）

观众是有一定编程或 AI 开发经验、想在几分钟内抓住项目大意的人。目标是“听完能用一句话复述这是什么、能做什么”，不是信息越多越好。

1. **开场要短**：开场 = 所选钩子 + 程序生成的一句榜单介绍（“榜单第几名，项目名，截止目前斩获 280K+ Star”）。钩子要一句话讲通透，不用“驱动、引擎、同一套”这类抽象词，用日常动作词。
2. **每段首句承接上一段**：用上一段的结论或悬念带出本段，例如“知道了它是做什么的，那它怎么做到？”“有了这一步，接下来……”。禁止每段都像重新开始。
3. **术语先解释再用**：MCP、二进制、x86、引擎、插件等，首次出现必须在同一句或下一句给出日常说法；没解释的术语宁可不用。
4. **结果检查段数字最多一个**：dashboard 只挑最能说明“它真的做到了”的一个数字，并说清这个数字代表什么，不并列多个指标。
5. **不讲安装和操作**：不出现安装命令、环境准备和“第一步、第二步”；适用对象和边界只在总结里用一句话带过。
6. **案例承接开场**：案例要回应钩子或现实麻烦里的同一个任务，不另起一个无关的例子。
7. **时长按项目复杂度自适应**：简单项目约 1.5 分钟，普通项目 2–2.5 分钟，复杂项目最多 3 分钟，不为凑时长重复内容。

其中开场句由程序生成；其余由提示词要求，并由“试听审核”抽检。
