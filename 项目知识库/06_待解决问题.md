# 待解决问题

1. 新项目仓库是继续使用用户提供的 MotionUtil 远程地址，还是创建独立远程仓库；当前未执行远程写操作。
2. 默认模型服务、默认模型名和 API 计费策略尚未确定。
3. 首个 Kokoro 中文默认音色、可用音色清单和 GPU/CPU 选择尚未确定。
4. `github-open-source` 默认包的备用源顺序、失败重试和过期快照策略需要在 M1 锁定；主源已固定为 `https://github.com/trending?since=weekly`。手动导入 PDF、网页和 Markdown 只能作为 AI 采集失败后的可选恢复入口，不是主流程前置条件。
5. BGM 的默认授权来源、音量标准和是否允许用户管理音乐库，尚未确定。
6. 字级强制对齐是否进入 MVP；当前建议 MVP 使用 beat/句级真实音频时长，M2 评估 forced alignment。
7. Three.js 场景复杂度、渲染时长上限和无 GPU 机器的降级规则需要样片验证。
8. 发布时是单文件 self-contained .NET EXE，还是 EXE 加固定运行时目录，需要在 M0 评估包体积和升级策略。
9. 需要在至少三个主题上做视觉验收：真实官网案例、无截图抽象动画、长文本和长命令输入；另需验证周榜 `batchCount>=10` 的隔离和续跑。
10. 需要在 M1 前确定随产品交付的 Kokoro 音色清单、发音词典覆盖范围和全量试听缓存容量上限；缓存失败重试与清理策略也需在性能测试中确认。

# M1 之后待解决问题

- 环境：FFmpeg 已从当前项目 Remotion 包自动发现并完成真实 MP4 渲染；新机器首次恢复依赖时的离线包缓存可用性仍待验证，继续遵守不复制旧项目依赖的约束。
- 真实任务：OpenAI-compatible `baseUrl`、模型名和 API Key 环境变量已配置；PowerShell `/models`、`/chat/completions` JSON Schema 探测成功，但 Node 原生 `fetch` 探测连接超时，需确认 Node 进程代理/网络出口后再跑真实周榜长流程，缺失时继续阻断，不回退到夹具。
- 真实任务：配置可用 Kokoro Runtime、音色清单和英文/数字发音抽检；测试夹具只用于显式测试模式。
- 媒体：BGM 库、授权来源、ducking 抽检和最终 true peak 测量仍需真实音频环境验证。
- 数据：真实周榜网络环境、备用源行为、长文本、官网案例和 `batchCount > 10` 的端到端环境冒烟仍待补充。
- M2：字级 forced alignment、更丰富的 Three.js 章节视觉、真实官网证据窗口和批量暂停/续跑体验优化。
